## 2. 核心业务流程（按角色）

### 学生/普通用户

```
1. 注册 → 登录 → 进入Dashboard
2. 看到 bootstrap 数据（通知列表、用户列表、自己的项目）
3. 上传通知文件（PDF/DOCX）→ AI解析通知 → 系统自动创建材料要求清单(material_requirement)
4. 基于通知创建项目 → 选择队长、指导教师、队员 → 系统自动初始化材料条目(project_material, status=pending)
5. 逐项上传材料文件 → 提交状态变为 submitted → 触发器自动计算完成率 → 项目状态变为 incomplete/ready
6. 点击"运行AI检查" → 系统提取所有已提交文件文本 → LLM审核 → 返回 pass/warning/reject + 详细评审意见
7. 如果AI检查不通过 → 自动收到通知消息(notify_message, msg_type=material)
8. 等待教师审核 → 查看审核意见 → 如被退回则修改后重新上传
```

### 教师/审核人

```
1. 登录 → 进入Dashboard（左侧菜单显示"我的项目"而非"总览看板"）
2. 在 TeacherDashboard 中看到自己作为 member 参与的所有项目列表
3. 选择某个项目 → 进入 MaterialReviewPanel
4. 查看各材料提交状态（已提交/未提交）和审核状态（已通过/待修改/未审核）
5. 点击文件预览查看材料内容
6. 逐项审核：通过(approved) 或 需修改(revision) + 填写修改意见
7. 如果退回 → 自动发送通知消息给项目负责人
8. 审核记录写入 review_record（review_type=teacher）
9. 支持重置审核状态（resetMaterialReview）
```

### 管理员

```
1. 登录 → 系统识别 role=admin → 直接进入 AdminDashboard（不加载 bootstrap）
2. 查看用户列表（支持关键词搜索）
3. 创建新用户（设置用户名/密码/真实姓名/角色）
4. 修改用户角色（student/teacher/admin）
5. 删除用户（逻辑删除，is_deleted=1）
```

**关键发现：管理员的 AdminDashboard 是一个完全独立的界面，不包含任何竞赛业务功能——既不能查看项目，也不能审核材料，也不能上传通知。管理员只能管理用户。**

## 3. AI 能力详细分析

### 3.1 通知解析（parseNoticeTool）

- **触发路径**: 前端 `NoticeUploadPanel` → `POST /notice/parse/{noticeId}` → `NoticeService.parseNotice()` → `AiService.parseNotice()`
- **模型**: `qwen-turbo`（DashScope OpenAI兼容接口）
- **输入**: 通知的原始文本（rawText），或从PDF/DOCX附件中提取的文本（Tika），上限4000字符
- **输出**: 结构化JSON `AiParseResult`（title, organizer, deadline, targetGroup, keyPoints, materials列表）
- **落库**: 
  - 更新 `competition_notice` 的 title/organizer/deadline/targetGroup/aiSummary
  - **删除旧的** `material_requirement` 记录，重新插入AI提取的材料要求列表
  - 写入 `agent_task_log`（toolName=parseNoticeTool）
- **失败兜底**: 返回 `fallbackParseNotice()` — 所有字段为null，keyPoints="AI解析暂时不可用，请稍后重试。"
- **问题**: 
  - AI 结果直接覆盖人工填写的表单字段（title总是被AI覆盖，organizer/deadline/targetGroup只在人工未填写时覆盖）
  - **有用户手动输入文本作为数据源**，但AI解析前会先检查rawText是否为空/系统占位符，如果只有PDF文件且Tika提取失败（扫描件），会抛出BusinessException而非兜底

### 3.2 材料检查（checkMaterialTool）

- **触发路径**: 前端 `MaterialCheckPanel` → `POST /agent/check-material/{projectId}` → `AgentService.checkMaterial()` → `AiService.checkMaterial()`
- **模型**: `qwen-turbo`
- **输入**: 项目上下文（名称/团队/截止日期/状态/完成率/缺失材料）+ 所有已提交文件的提取文本（Tika 提取，有100K字符上限）
- **输出**: 结构化JSON `AiCheckResult`（reviewResult: pass/warning/reject, reviewComment: 中文评审意见）
- **两阶段逻辑**:
  1. 如果没有可提取文本的文件 → 仅基于完成率判断（全部提交=pass，有缺失=warning）
  2. 如果有文件文本 → LLM审核 + 材料缺失合并（missing materials强制设为warning，LLM结果附加在内容审核部分）
- **落库**: 
  - 写入 `review_record`（review_type=ai）
  - 写入 `agent_task_log`（toolName=checkMaterialTool）
  - 如果结果不是pass → 写入 `notify_message` 通知项目负责人
- **失败兜底**: 返回 `fallbackCheckMaterial()` — reviewResult="warning", reviewComment="AI审核服务暂时不可用，系统已自动标记为待人工复核。请人工审核项目材料。"

### 3.3 PDF OCR 视觉识别

- **触发路径**: `FileTextExtractor.extractText()` → Tika提取失败 且 文件扩展名为pdf → `PdfOcrExtractor.ocrPdf()`
- **模型**: `qwen-vl-plus`（DashScope视觉模型）
- **流程**: PDFBox渲染页面为BufferedImage（100DPI, 最大宽度1200px）→ JPEG压缩（质量0.75）→ Base64编码 → 发送给视觉模型 → 多个页面**并行**调用
- **限制**: 最多3页，单页超时120秒，单页图片最大2.5MB
- **失败兜底**: 返回null → Tika的失败占位符被返回 → 调用方收到 `[No extractable text found in file]`

### 3.4 是否有人工确认？

**没有。** AI 的结果直接写入数据库，没有任何"人工确认"环节：
- 通知解析：AI结果直接更新 notice 字段，直接替换 material_requirement 表
- 材料检查：AI结果直接写入 review_record 和 notify_message
- 唯一的人工环节是教师的材料审核（MaterialReviewPanel），但那是独立的业务流程

### 3.5 AI 失败兜底总结

| 场景 | 兜底行为 |
|------|---------|
| DASHSCOPE_API_KEY 未设置 | `@PostConstruct` 打印WARN日志，AI功能返回降级结果，不影响系统运行 |
| LLM API 调用异常 | catch Exception → 返回 fallback 结果（parseNotice返回全null，checkMaterial返回warning） |
| LLM 返回非JSON | `cleanJson()` 尝试提取最外层 `{...}`，失败则 Jackson 抛异常 → 进入fallback |
| 文件无文本内容 | 跳过LLM调用，仅基于完成率判断 |
| Tika 提取失败 + PDF | 自动切换 OCR 管线 |
| OCR 也失败 | 返回Tika的失败占位符，上层会显示 "无可审核的文件内容" |

## 4. 数据库核心表及关系

### 10张表，关系图：

```
sys_user ──────────────────────────────────────────────────────
  │         │           │              │            │
  │         │           │              │            │
  │     (uploaded_by)   │         (reviewed_by) (receiver_id)
  │         │           │              │            │
  ▼         ▼           │              ▼            ▼
file_asset  │     competition_project  │      notify_message
  │         │         │      │         │
  │    (created_by)   │      │    (reviewer_id)
  │         │         │      │         │
  │         ▼         │      │         ▼
  │  competition_notice│      │    review_record
  │         │         │      │    (project_id)
  │    (notice_id)    │      │
  │         │         │      │
  │         ▼         │      │
  │  material_requirement    │
  │    (notice_id)    │      │
  │         │         │      │
  │    (requirement_id)      │
  │         │         │      │
  │         ▼         ▼      │
  │    project_material ─────┘
  │    (project_id, requirement_id, file_id)
  │
  └── project_member
      (project_id, user_id)
```

### 核心设计模式：
- **通知 → 材料要求**: 一对多（`material_requirement.notice_id`）
- **通知 → 项目**: 一对多（`competition_project.notice_id`）
- **项目 → 项目材料**: 通过 `material_requirement` 间接关联，`project_material` 有两个外键（project_id + requirement_id），**加上 version_no 形成唯一约束**
- **项目 → 成员**: 多对多（`project_member` 有 project_id + user_id 唯一约束）
- **文件存储**: `file_asset` 既存 LONGBLOB（当前方案），又预留 storagePath（MinIO/S3 扩展）

### 特色设计：
- **版本追踪**: `project_material` 的 `(project_id, requirement_id, version_no)` 唯一约束，支持材料多版本提交，查询时取 MAX(version_no)
- **自动刷新**: 触发器和存储过程自动计算 completion_rate 和 project status
- **所有表**都有 `is_deleted` 字段做逻辑删除（MyBatis-Plus @TableLogic）
- **所有表**都有 `created_at` 和 `updated_at`

## 5. 权限控制审查

### 5.1 后端权限：**几乎不存在**

```java
// SecurityConfig.java:27
.authorizeHttpRequests(auth -> auth.anyRequest().permitAll());
```

**所有接口全部放行！** Spring Security 只做了：
- 关闭 CSRF
- 开启 CORS
- 设置无状态会话
- 然后 `.anyRequest().permitAll()` 放行一切

**没有注册 JWT 过滤器**。JWT 只在个别 Controller 中手动提取和使用：
- `UserController.resolveCurrentUser()` — 手动从 Header 取 token，解析 userId
- `ProjectController.extractUserId()` — 同上，但 `/my-projects` 如果没token返回401
- `DashboardController.bootstrap()` — JWT提取是可选的（userId可以为null）

**这说明系统没有统一的认证拦截层。** 每个接口自行决定要不要检查JWT。

### 5.2 存在默认 userId 硬编码

| 位置 | 默认值 | 说明 |
|------|--------|------|
| `NoticeController.java:36` | `createdBy = defaultValue = "1"` | 通知上传人默认为 userId=1（admin） |
| `MaterialController.java:32` | `uploadedBy = defaultValue = "3"` | 材料上传人默认为 userId=3（student1） |
| `competition.js:32` | `createdBy ?? 1` | 前端也硬编码默认值 |
| `competition.js:40` | `uploadedBy ?? 3` | 前端也硬编码默认值 |

只要不传 `createdBy` 或 `uploadedBy` 参数，操作就默认以 userId=1 或 userId=3 的身份执行。

### 5.3 前端权限代替后端权限

- `App.vue` 根据 `currentUser.role` 切换视图（student/teacher/admin）
- 管理员进入 `AdminDashboard`，教师进入 `TeacherDashboard + MaterialReviewPanel`，学生进入普通面板
- **但这纯粹是前端 UI 切换，后端接口不做角色校验**
- 理论上：学生可以直接调用 `/material/review` 接口审核材料（只要传一个 teacher 角色的 reviewerId）

### 5.4 具体权限漏洞

| 漏洞 | 影响 |
|------|------|
| `/admin/users` 无鉴权 | 任何人可以列出所有用户 |
| `/admin/users/{userId}/role` 无鉴权 | 任何人可以修改任何人的角色 |
| `/admin/users` POST 无鉴权 | 任何人可以创建管理员账户 |
| `/admin/users/{userId}` DELETE 无鉴权 | 任何人可以删除用户 |
| `/notify/messages?receiverId=X` 无鉴权 | 任何人可以查看任何人的消息 |
| `/material/review` 无鉴权 | 任何人可以伪装成教师审核 |
| `/material/upload` uploadedBy 可控 | 可以以任何人的身份上传材料 |

## 6. 项目最像什么系统？

**最像：竞赛材料管理系统 + 轻量OA审核流的混合体。**

具体来说：
- 核心数据模型是"通知→项目→材料"，这是典型的**竞赛申报系统**
- 有状态流转（draft → incomplete → ready → reviewed），这是**OA审批流系统的雏形**
- AI 做材料内容审核，这是**AI辅助审核系统的探索**
- 但OA能力非常初级：没有多级审批、没有驳回重走流程、没有审批链配置

如果非要选一个标签，它是：**带有AI辅助检查功能的竞赛材料管理系统**。

## 7. 作为 Java 后端实习项目，最容易被面试官质疑的问题

### 7.1 🔴 致命问题：Spring Security 形同虚设

```java
.authorizeHttpRequests(auth -> auth.anyRequest().permitAll());
```

你引入了 Spring Security + BCrypt + JWT 全套依赖，但**没有注册任何 AuthenticationFilter**。JWT 的生成和解析代码都写了，但只是放在工具类里备用。面试官一定会问："你的 JWT 是怎么生效的？在哪里拦截未登录请求？"

### 7.2 🔴 默认 userId 注入

`NoticeController` 和 `MaterialController` 中 `createdBy`/`uploadedBy` 使用 `defaultValue` 从请求参数中取。这意味着**请求方可以伪造身份**。面试官会问："如果有人用Postman传 `createdBy=2` 会发生什么？"

### 7.3 🔴 没有统一的用户身份获取机制

`UserController` 用 `resolveCurrentUser()`，`ProjectController` 用 `extractUserId()`，`DashboardController` 又写了一遍。这是典型的"开发者不知道 Spring Security Context 怎么用"的信号。

### 7.4 🟡 垂直越权零防护

`ProjectService` 的所有方法都接受任意 `projectId`，不校验当前用户是否是该项目的成员。任何人都可以通过修改 projectId 查看/操作任何项目。同样，`MaterialService.reviewMaterial()` 只校验 reviewerId 是否存在，不校验是否是教师。

### 7.5 🟡 密码硬编码在 sql.py 且泄露到仓库

```python
# sql.py:7
password="AVNS_xxxxx（已轮换，示例密码）",
```

这是 Aiven MySQL 的真实密码，已提交到 Git。另外 V1 迁移中的演示用户密码都是同一个 BCrypt hash，实际密码未知但不能保证不是弱密码。

### 7.6 🟡 文件存储在数据库 LONGBLOB

README 说"预留 MinIO/S3 扩展路径"，但实际所有文件都存数据库。50MB 限制 × 多版本 × 多材料 = 数据库迅速膨胀。面试官会问："为什么不用 OSS？你考虑过数据库备份和恢复时间吗？"

### 7.7 🟡 通知解析会删除并重建材料要求

`NoticeService.parseNotice()` 第160-163行：`materialRequirementMapper.delete(...)` 无条件删除所有旧要求再插入新的。如果已有项目关联了这些旧要求，数据一致性会出问题。

### 7.8 🟢 单测试类问题

`AicompetitionApplicationTests.java` 是 Spring Initializr 生成的默认测试，只测了上下文加载。没有任何业务逻辑测试。

## 8. 最值得保留的亮点

### 8.1 ✨ PDF 两阶段提取管线

`FileTextExtractor` + `PdfOcrExtractor` 的设计很完整：
- Tika 先尝试文本提取
- 失败时自动降级到 PDFBox 渲染 + 多模态视觉模型 OCR
- 多页并行处理 + 超时控制 + 图片大小限制
- 全程不抛异常，每个环节都有兜底
- 这是项目中**工程化程度最高的模块**

### 8.2 ✨ 材料版本追踪设计

`project_material` 的 `(project_id, requirement_id, version_no)` 唯一约束 + 查询时取最新版本 + 上传时自动判断是覆盖旧版本还是创建新版本，设计思路清晰。

### 8.3 ✨ 数据库触发器 + Java 双重保障

完成率计算既有 DB 触发器自动刷新，又有 Java 代码显式调用 `refreshProjectProgress()`。这种"数据库层保障 + 应用层显式控制"的组合是好的工程实践。

### 8.4 ✨ AI 失败不阻塞业务流程

所有 AI 调用都有 try-catch + fallback，失败时返回降级结果而非抛异常。这保证了系统在 AI 服务不可用时仍然可用。

### 8.5 ✨ Dashboard Bootstrap 聚合接口

一个接口返回通知、用户列表、项目详情、进度、AI审核结果，减少了前端的请求次数。虽然实现方式粗暴（Controller 里写大量逻辑），但思路是对的。

### 8.6 ✨ 前端 Mock 模式

三套完整的 Mock 服务（auth/competition/user），支持离线开发和演示，对实习项目来说很加分。

## 9. 当前项目真实画像（5句话总结）

1. **这是一个由单人开发的毕业设计/课程项目级别的竞赛材料管理系统**，技术栈为 Spring Boot 3 + Vue 3 + MyBatis-Plus + MySQL，代码量适中（~62个Java文件 + ~16个Vue组件），结构清晰但深度不足。

2. **系统实现了从"上传竞赛通知→AI解析→创建项目→上传材料→AI检查→教师审核→消息通知"的完整业务流程**，每个环节都有基本实现，但缺少边界条件处理和异常路径覆盖。

3. **AI 能力是真实集成的**（阿里云 DashScope qwen-turbo + qwen-vl-plus），不是 mock 或演示效果，PDF 的 OCR 两阶段降级管线设计得不错，但 AI 结果直接落库，无人工确认环节。

4. **权限控制是该项目最大的短板**：Spring Security 配置为 `.anyRequest().permitAll()`，JWT 没有注册拦截过滤器，多个接口存在默认 userId 注入，管理员接口无任何鉴权——这使其不能直接用于生产环境。

5. **对于 Java 后端实习项目而言，这个项目展示了基本的 CRUD 能力和第三方 API 集成能力，但暴露了安全意识的缺失、缺少单元测试、以及没有统一的认证/鉴权架构设计**——如果面试时能把权限问题讲清楚并给出改进方案，反而是一个好的话题切入点。
